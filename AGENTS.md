# AGENTS.md

Guidance for agents working **in this repo** (editing the viewer/tooling or the skill doc). For using the skill to build DAGs, read `skill/SKILL.md` and `README.md` instead. `CLAUDE.md` is a symlink to this file — edit here, don't replace the link.

## Project shape

Two independent modules in one npm-workspaces repo (`workspaces: [server, web]`):

- **`skill/SKILL.md`** — a published agent skill (frontmatter + prose): a deliberately **thin** project workflow (PRD → technical design → task DAG → viewer). It resolves the correct Orca CLI, loads the runtime-matched guide with `orca skills get orchestration`, and delegates all command syntax and lifecycle rules to that guide — hard-coded command copies drift from the installed runtime, and `scripts/check-skill.mjs` rejects them. No code; edit it like a doc, keep frontmatter intact.
- **`server/` + `web/`** — the `orca-dag` viewer: an Express API + React Flow SPA that visualizes a Run's DAG and runs a self-driven coordinator loop. Compiles to a single portable binary (`dist/orca-dag`).

This repo is a thin, heavily-commented wrapper over the `orca` CLI. Every Orca quirk is documented in `server/src/orca.ts` comments — **read them before touching orchestration code.**

## Commands

```bash
npm install
npm run dev            # BOTH server (:8787) + web (:5173) via concurrently; vite proxies /api → :8787
npm run dev:server     # tsx watch src/index.ts (server only)
npm run dev:web        # vite (web only)
npm run build          # web only: tsc -b && vite build → web/dist
npm run build:binary   # web build → embed as base64 in server/src/generated/webAssets.ts → bun --compile → dist/orca-dag
npm run build:npm      # web build → esbuild the server → dist-npm/ (the publishable `orca-orchestration-launcher` package; Node only, no Bun)
npm start              # server (tsx) against web/dist on disk; needs `npm run build` first for UI
```

- **Root scripts exist** (`typecheck` / `test` / `check:skill` / `check`): `npm run typecheck` covers both packages (`tsc -p server/tsconfig.json --noEmit && tsc -b web`), `npm test` runs the server suite, `npm run check:skill` validates SKILL.md, and `npm run check` chains them — skill → typecheck → tests → web build. CI runs exactly `npm run check` (plus an `npm audit --audit-level=high` gate), so keep local and CI on the same script.
- **Tests exist server-side only** (`npm test -w server`, `tsx --test src/*.test.ts`, Node's built-in runner — no second test framework). `orca.test.ts` covers CLI/workspace resolution, readiness gating and coordinator conflicts against a fake `orca` executable; `app.test.ts`/`security.test.ts` cover the HTTP surface. There is no web test target yet.
- **`build:binary` requires `bun` on PATH** (not declared as a dependency). Cross-compile with `TARGET=bun-linux-x64 npm run build:binary`.
- Binary runtime env: `PORT` (8787), `NO_OPEN=1` (skip browser), `WORKSPACE_DIR` (an existing directory, resolved to its realpath — becomes the exact `path:` worktree selector), `ORCA_WORKTREE` (explicit selector, overrides the `path:` default), `ORCA_CLI_COMMAND` (exact Orca CLI as quoted argv, parsed with **no shell** — operators/redirections/substitution are rejected).

## Distribution

Two artifacts ship from this repo today. Orca's plugin system is now in alpha (no longer experimental), and building an Orca plugin form of this project is allowed; author one with `orca skills get orca-plugin-authoring` as the source of truth for the installed runtime. Orca also deliberately ships no scheduler ("A Run is a namespace and home inbox. It never schedules or places workers."), so an external coordinator like this one is the intended shape, not a workaround.

- **`npx orca-orchestration-launcher` is the whole install.** `server/src/skill.ts` detects existing agent configuration roots and installs `skill/SKILL.md` before the server listens. Shared agents use the canonical `.agents/skills` root; native agent roots and absolute relocated homes (`CLAUDE_CONFIG_DIR`, `GROK_HOME`, `KIRO_HOME`, `CODEX_HOME`) resolve through `resolveAgentSkillDirs`. Never populate an agent-free HOME. Simple legacy shared-agent installs may move to the canonical location only without overwriting an existing destination; preserve non-simple user content. Installation must stay best-effort: never throw, never rewrite an unchanged file, and **never follow symlinked ancestors, skill directories, or skill files** (the `ln -s "$PWD/skill"` recipe must not clobber a working copy). `--no-skill` / `ORCA_DAG_NO_SKILL=1` opts out.
- **Planning docs live in `.orca-dag/<UTC timestamp>/PRD.md` and `TECH_SPEC.md`**, one directory per new requirement/replanning Run; the skill owns directory creation and records the Run id. `server/src/planning.ts` initializes only a marked `.orca-dag/` block in the workspace's `.gitignore` at viewer startup and explicitly reports it. Keep it idempotent/best-effort, preserve user rules, never write through symlinks. `--no-workspace-init` / `ORCA_DAG_NO_WORKSPACE_INIT=1` is independent of `--no-skill`. Plans are ignored, never force-added to Git; Task specs must embed required context for isolated workers. Legacy `.orca/` docs and their ignore protection are untouched at startup. Uninstall removes only exact managed ignore blocks for either location and **always preserves planning docs, even with `--purge`**.
- **All five viewer state stores live in `.orca-dag/`**: `config.json`, `activity.jsonl`, `launches.jsonl`, `requests.jsonl`, `sessions.json`. `server/src/workspaceState.ts` owns paths for every store and uninstall, creates the shared directory on writes, and moves legacy root `.orca-dag.*` files byte-for-byte without overwriting destinations. Constructors must stay side-effect-free; startup migration runs **after acquiring the HTTP port**, so a failed second launch cannot move an older viewer's state. Stop older viewers before upgrading. Conflicts use the new file, keep the legacy file and warn; unwritable migrations retain read-only access to legacy regular files but writes never return to the old layout. Never follow symlinked data directories/files. `--no-workspace-init` skips ignore-rule changes, not state persistence/migration.
- **`orca-dag uninstall` (`server/src/uninstall.ts`) is the mirror image and has to stay that way** — anything a future startup step writes outside the workspace must get a matching removal here, or the install becomes a one-way door. It shares `resolveAgentSkillDirs`/`SKILL_NAME` with `skill.ts`, including detected native, canonical shared, legacy, and relocated roots. Use the same home overrides when uninstalling; skip symlinked ancestors, but unlink a final symlinked skill directory rather than following it. It keeps `.orca-dag/config.json` and other history unless `--purge` (real user work), and closes every terminal whose title starts with `COORDINATOR_TITLE` — a crashed viewer otherwise leaves one bound to the Run, fencing the user's own agent. Purge enumerates known state files in both layouts and Git evidence, **never recursively deletes `.orca-dag/`**; timestamp planning folders and other files stay intact. Ordinary uninstall and `--dry-run` must not trigger migration.
- **Subcommands are dispatched at the top of `index.ts`**, before the express app is built, so `uninstall` and `--help` never bind a port, create an Orca terminal, or install the skill on their way out. Keep new subcommands in that block.
- **The skill** also installs through the community skills CLI straight from this repo: `npx skills add yyq19990828/Orca-dag --skill orca-dag`. Discovery keys off `skill/SKILL.md`'s frontmatter — `scripts/check-skill.mjs` guards it in CI (don't shell out to `skills add . --list` there; it prompts when no agent is detected and hangs). The same script rejects drift: the body must load `skills get orchestration`, state the 1.4.205 execution baseline, and contain no fenced copy-paste orchestration mutation command lines — command syntax belongs to the runtime-matched guide.
- **The binary embeds the skill too** (`SKILL_MD` in the generated `webAssets.ts`, next to `WEB_ASSETS`) — it has no package directory to read from, and a single downloaded file has to behave like the npm package. CI boots it with a throwaway `HOME` and greps the installed copy for `skills get orchestration`, so the embed can't go stale when the skill changes.
- **The viewer** publishes as the `orca-orchestration-launcher` npm package (`npx orca-orchestration-launcher`), plus standalone Bun binaries attached to the GitHub release for people without Node. **Naming convention for this fork:** the *published package name* is our own (`orca-orchestration-launcher` — upstream owns `orca-dag` on npm, so `npx orca-dag` resolves to *their* package and must never appear in user-facing copy), while the `bin`/global command, the skill name, and every runtime trace (`.orca-dag/config.json`, the `orca-dag coordinator` terminal title, `SKILL_NAME`) deliberately stay `orca-dag`. `scripts/build-npm.mjs` stages `dist-npm/`; the bundle lands at `dist/server/index.mjs` **on purpose** — `index.ts`'s disk fallback looks in `join(__dirname, "..", "..", "web", "dist")`, which only resolves inside the package at that depth. Moving either path breaks the SPA silently (API still answers, UI 404s), which is exactly what the CI smoke test checks.
- Inside Orca, the viewer surfaces via `orca tab create --url` (already how `openBrowser` works) — a real Electron browser tab with no CSP restrictions.
- **After the one-time npm package bootstrap, releasing is one command: `npm run release <version>`** (`scripts/release.mjs`) — it refuses a dirty tree, a non-`main` branch, a bad semver or an existing tag, runs the checks, then tags and pushes. `.github/workflows/release.yml` takes it from there. **The tag is the version of record for stable releases** — `PKG_VERSION` overrides the staged `package.json`, so the repo's own version never needs bumping in a commit.
- `.github/workflows/ci.yml` runs `npm run check` (skill validation + typecheck + tests + web build) plus an npm-audit gate, then stages the package and boots the packed tarball on plain Node. `release.yml` publishes to npm with provenance and cross-compiles every binary target from one Linux runner.
- **npm publishing uses Trusted Publishing (OIDC), with no `NPM_TOKEN` secret.** The npm job runs Node 24 and npm >=11.5.1 with `id-token: write`; npm authenticates the exact `yyq19990828/Orca-dag` + `release.yml` GitHub Actions identity and generates provenance. npm requires an existing package before a Trusted Publisher can be configured. Bootstrap once with a locally authenticated, 2FA-protected `1.0.0-oidc-bootstrap.0` publish under the `bootstrap` dist-tag, then configure the npm package's Trusted Publisher to allow `npm publish` before pushing the first stable release tag. README/README_zh give the exact steps.
- **A failed OIDC publish is recoverable without burning a version.** If npm rejected the publish, correct the Trusted Publisher mapping and `gh run rerun <run-id> --failed`. The rerun checks out the same tag, so it publishes exactly the tagged tree regardless of what has since landed on main. Don't cut a new version for an authentication error.

## Architecture gotchas

- **The viewer is the scheduler.** Orca ships no scheduler by design (`run`/`run-stop`/`coordinator-start`/`coordinator-stop` are retired no-ops). `server/src/coordinator.ts` owns the dispatch loop: each tick starts a worker for every `ready` task up to `maxConcurrency`.
- **Authority model shapes the whole server.** Reads (`task-list`/`gate-list`) need only `--run <id>` (any process). This external viewer performs mutations from its live terminal bound to the Run via `--from <handle>`; Orca-native chats may instead use their own session identity. So the server keeps its own "orca-dag coordinator · <workspace-hash> · <instance-id>" Orca terminal for pane identity (`ensureCoordinatorTerminal` in `orca.ts`). The hash scopes the terminal to one workspace: another viewer on a *different* workspace can never adopt it, and another viewer on the *same* workspace gets `coordinator_conflict` (never silent reuse, never close). The stable `orca-dag coordinator` prefix is uninstall's discovery contract — don't change it.
- **CLI + workspace resolve once, at startup** (`initOrcaRuntime` in `orca.ts`, called from `index.ts`): resolution order is `ORCA_CLI_COMMAND` → `orca-dev` when `ORCA_DEV_REPO_ROOT` is set → `orca-ide` on Linux *outside* a managed Orca terminal (bare `orca` there is GNOME's screen reader at `/usr/bin/orca`) → `orca`. Every CLI call spawns the resolved `{ executable, prefixArgs }` with `shell: false` and `cwd: <workspace>`. `WORKSPACE_DIR` must exist and is `realpathSync`'d, so symlinked spellings of the same directory share one identity (and one coordinator-title hash).
- **`asCoordinator` (index.ts, app.ts) never reuses the loop's terminal** for one-off mutations — it creates a throwaway, uniquely-titled terminal, binds, acts, closes. Reusing the loop's terminal would fence and then kill a running coordinator. For mutations on inactive, unbound, or external Runs (`POST /api/messages/:id/reply`, `POST /api/gates/:id/resolve`, `POST /api/gates`, `POST /api/workers/:dispatchId/resolve-blocked`), `asCoordinator` does NOT implicitly take over coordinator authority: it requires explicit operator confirmation matching current Run binding evidence (`coordinatorControl: { confirmed: true, coordinatorHandle: string | null, consumerGeneration: number | null }`), throwing `409 coordinator_control_required` otherwise. Never silently create or bind a terminal without explicit consent.
- **`dispatch --inject` does not reliably submit** the preamble into the agent TUI. `startLegacyWorker` sleeps ~2s then sends an Enter; a stray Enter on already-submitted input is an intentional no-op. Don't "fix" this.
- **OpenCode Auto routing:** the viewer harness `opencode` runs OpenCode 2. Without a model, running Orca ≥ 1.4.220 uses native `opencode2`. An explicit model can use native `opencode` only on stable running Orca ≥ 1.4.241 with launch preferences advertised, local POSIX current/existing non-lane placement, no variant/effort, and no API-TUI opt-in. Execution-host CLI/model preflight remains authoritative. Other cases retain one-shot `opencode run --auto -m` compatibility and its placement limits; explicit frontends and API opt-in keep their session adapters. Native refusal never authorizes a second launch.
- **OpenCode model support is agent-specific.** The generic `orchestration.worker-launch-preferences.v1` advertisement does not prove `opencode2 --model` support. Orca 1.4.222 fixes submission readiness but does not meet the viewer's newer model-route floor; do not add Enter retries. Orca 1.4.241 expands verified native `opencode` CLI versions and excludes versions that lose the first prompt. New-worktree model overrides and native OpenCode effort remain unsupported. All OpenCode workers are excluded from generic reuse to preserve pinned/default-model and frontend/session identity. Unified shell-safe model grammar `/^[A-Za-z0-9._-]{1,128}\/[A-Za-z0-9][A-Za-z0-9._:/-]{0,511}(?:#[A-Za-z0-9._-]{1,128})?$/` supports slash-namespaced model IDs after the first slash (e.g. `openrouter/meta-llama/llama-3.1-70b-instruct#high` or vendor/model when vendor contains slashes), agreed across UI, discovery, API and security validation.
- **Helpers, mailbox ownership, and version terminology:** Upstream public orchestration contract is `contract 1` (`orchestration.contract.v1`), runtime protocol is 3, federation lifecycle settlement protocol is 3 (`ORCHESTRATION_FEDERATION_LIFECYCLE_SETTLEMENT_PROTOCOL_VERSION`), and control mail protocol is 2; `orchestration.federation-lifecycle-settlement.v1` is the settlement capability. Local V3 migration and the `[orca-dag:merge-inputs-v3]` handshake marker are local viewer contracts/markers, NOT a global upstream version; never rename persisted markers. `workerOwnership.ts` reads exact Dispatch creator lineage, discovered through hierarchical Task/fleet hints; active creators retain helper custody, unreadable evidence holds, and only positive creator settlement hands work back. Never treat Task parent as mutation authority or stop a delegated helper on the creator's behalf. Max concurrency is viewer admission against visible fleet, not a runtime-wide helper cap. Legacy FIFO ACK may return the next Delivery; consuming check acknowledges on read and ACK alone does not fetch another batch. Persist pending processing, guidance sends, and operator messages in `.orca-dag/sessions.json` (`mailboxChecks`, `guidanceSends`, `operatorMessages`); these critical recovery journals serve as recovery authority, not rotating audit logs, and cannot safely be hot-downgraded across unsupported readers. Inactive reply and group send helpers (`operatorMessages.ts`) checkpoint UUID, body hash, and scope in `operatorMessages` before Orca calls, recovering unknown states via read-only `request-show` (`operator_message_reconciled` on prior completion with different body, `operator_message_unknown` on unresolved). Native exact SAME-UUID recovery for worker starts/releases remains supported. StopReason escalations (`finished`, `errored`, `needs-input`, `exited`) are events (`PendingInboxItem.kind === 'stop_event'`), distinct from replyable questions (`kind === 'question'`); resolution must follow exact Dispatch steering, operator decisions, or authoritative later settlement, never synthesizing replies or success. Guidance sends support positively evidenced `recipient_run_bound_redirect`, distinguishing originating Task/Dispatch Run from actual destination mailbox/Run without child authority adoption or false worker creation. `listWorkers` returns typed `WorkerInventory` (`{ workers: OrcaWorkerRow[], partialHostErrors: unknown[] }`), aggregating `partialHostErrors` across all pages; missing remote hosts make absence unsuitable for lifecycle decisions, and host errors never infer exit or clear debt.
- **OpenCode interface selection:** `defaultOpenCodeUi` / `openCodeUiByTask` choose `auto` (legacy behavior), `mini`, or `tui`; the node override wins and only affects OpenCode. Explicit frontends use `startOpenCodeInteractiveWorker` on local Linux current/existing non-lane workspaces, running Orca ≥ 1.4.222 and CLI ≥ 2.1.2; no generic terminal reuse or fallback after refusal. Both share the existing API-prepared session lifecycle. Mini has no `--auto`: preserve configured permissions. Journal `frontend` and `requestedModel` separately from resolved `model`; model may be null only without a pane/Dispatch and can resolve once before pane creation. Old rows normalize to full TUI. A provider-resolved default variant is allowed only when unspecified by the request; explicit variants remain strict. Additional user messages (including unproven nudges) conservatively retain ownership. New journal fields require a compatible reader; do not hot-downgrade over unresolved preparations. `auto` preserves all historical native/one-shot/env routing below.
- **Opt-in API-preselected full TUI:** `ORCA_DAG_OPENCODE_TUI=1` changes only explicit OpenCode model selections on local POSIX current/existing non-lane placements, requiring running Orca ≥ 1.4.222. `openCode.ts` owns bounded V2 API/model/execution evidence; `ProviderSessionStore` keeps additive request-scoped `openCodeLaunches` alongside bindings in `sessions.json`, written before preparation effects. The adapter binds through `worker-start --terminal` without model/effort/agent wire flags. API evidence is not Orca effective launch or Task settlement. External release does not close the pane; caller-owned cleanup requires exact identity, accepted settlement and positive provider execution exit. Stop interrupts the exact shared-service session before Orca accounting. User prompts and explicit retain preserve ownership. Unresolved preparations block replacements even when the flag/harness later changes. Never enable generic terminal reuse for these model-pinned sessions. No new state file or global config modification.
  - **External Stop is not native worker-stop.** After positive API execution exit, this adapter selects `worker-abandon` for Orca-only accounting (and journals that exact operation). 1.4.222 native stop leaves external Dispatches `stop_unknown` even after provider interruption. Re-read cancellation settlement before release. Post-fence `retained / identity_unproven` is deliberate retention for inspection, never an automatic pane close. This is chosen before mutation, not a fallback after unknown Stop. Active/blocked exact prepared Dispatches remain held on recovery even if `task.dispatch_id` is absent and `workerState` is a lifecycle stage.
  - **Full-TUI startup is not shell idle.** Use a request-local `OPENCODE_TUI_CHANNEL` to isolate restored tabs without changing shared-service discovery or global configuration. Wait for the exact session-derived `OC | odag:<request>` title before `tui-idle` and binding; creation-title equality alone does not prove that OpenCode mounted. V2's omitted variant and wire `default` are equivalent, never wildcards for provider/model or an explicit variant. Keep the stricter startup check separate from recovery/cleanup identity checks.
- **Viewer presets require recorded execution verification:** `claude`, `codex`, `opencode`, `omp`, and `antigravity` are selectable built-ins, within their documented version/path limits. Distinguish independent native baselines from viewer/restart checks; do not claim unrun cells passed. Orca's native agent registry and agent skill installation are not worker verification. `gemini`, `grok`, `cursor`, `droid`, and `kimi` remain unavailable; reject their bare IDs with `unverified_harness` even with custom commands enabled, including saved plans and retries. Never silently replace stored selections or discard historical rows.
- **OMP / Antigravity use native preference-following launches:** both resolved CLI and ready running runtime must be ≥ 1.4.245 for local Linux Current/exact Existing; new Git worktrees or lanes require both ≥ 1.4.246. Remote, macOS and Windows routes remain unsupported. Use `worker-start --agent omp` / `--agent antigravity`, never prelaunch with `agent launch --surface terminal` then bind with `--terminal`. Orca settings choose Chat/Terminal; do not inspect/reject the preference, force a surface, or write settings. Independent Terminal TUI baselines used OMP 18.15.0 and Antigravity 1.4.12. OMP Native Chat has separately recorded execution, recovery and Stop evidence; Antigravity Chat remains unverified. Pass a complete opaque selector as one native `--model` argument or omit it for the configured default; reject every nonempty effort and preserve saved unsupported values until explicit clearing. Native Chat ACP identifiers need not accept CLI thinking suffixes: 1.4.247 rejected `openai-codex/gpt-6.1-terra:xhigh`; do not normalize it or retry another route. No generic terminal reuse or fallback after native refusal/unknown; native semantic send may reuse a chat and its exact returned identities/launch-mode tuple remain authoritative evidence. Preserve requested/effective/liveness/custody/unknown receipts. OMP supports bounded transcripts and normal-release archives; Antigravity uses terminal fallback (`provider_unsupported`) and normal-release terminal archives. Historical post-active-Stop archives were unavailable; do not infer archival from settlement. Antigravity 1.4.10 drift and the rejected forced-Terminal design remain historical, unverified evidence; do not alter their retained resources.
- **Per-node model override (`modelByTask` in `.orca-dag/config.json`)** is only wired for harnesses that support it: **opencode** (enumerable via `opencode models` → `listModels` in `orca.ts`, routing gates above), and **claude/codex/omp/antigravity** (free-text; the latter two follow the native limits above). Claude passes the model through `worker-start --model`. Local POSIX Codex in a current/existing worktree uses native `worker-start --agent codex --model` on a **running Orca ≥ 1.4.217**, which fixes readiness and per-terminal server isolation; inspect `status.runtime.appVersion`, not the CLI version. Older/unknown runtimes prestart with `codex -m` and bind via `worker-start --terminal`; `--terminal` cannot combine with `--model`/`--effort`. This compatibility path requires two stable empty-composer screen frames, rejects `model: loading`, and must not require a `model:` footer (Codex 0.159.2 uses `GPT-…`). Local new-child/new-top-level placements retain create → verify base SHA → launch in the positively identified startup shell → bind, until that separate path is accepted end to end. Remote and Windows Codex retain native starts. Native failure never authorizes an automatic compatibility retry. Other harnesses without per-node model controls retain their existing behavior. The dispatch loop threads model/effort through the selected adapter; shell-command arguments are quoted.
- **Viewer must run inside an Orca-managed worktree** — `orca terminal create --worktree` needs the cwd to be registered (`orca repo add`/`orca worktree`), else `selector_not_found`.
- **Launch the viewer from the repo root with a clean Orca environment.** `WORKSPACE_DIR` unset means the process cwd becomes the workspace — starting from a subdirectory (e.g. `server/`) resolves the worktree selector to an unregistered path (`selector_not_found` on every execution mutation). And when started from *inside* an Orca-managed terminal (or any shell with Orca env), the inherited `ORCA_TERMINAL_HANDLE` attests every viewer CLI call as *that* terminal, so the viewer's freshly created coordinator terminal is refused (`consumer_fenced: This terminal is attested as …`). The safe launch is:
  ```bash
  env -u ORCA_TERMINAL_HANDLE -u ORCA_TAB_ID -u ORCA_WORKSPACE_ID -u ORCA_WORKTREE_ID \
      WORKSPACE_DIR="$PWD" npm start
  ```
- **Worker terminals must not show a blocking dialog when the coordinator injects the preamble.** Orca scans the terminal for trust/update/permission prompts (`agent_prompt_blocked`) and refuses `dispatch --inject` if one is on screen — a fresh `claude` TUI asking "Do you trust the files in this folder?" (first launch in a directory without a `hasTrustDialogAccepted` entry in `~/.claude.json`) or an "update available / press enter to continue" notice both count. A `start_failed` attempt PARKS its task: the coordinator never auto-retries (plan removes auto-retry); the user must Stop (`POST /api/run-stop` — there is no `/api/stop`) and Run again after fixing the cause. Pre-trusting the workspace root in `~/.claude.json` (`"projects": { "<root>": { "hasTrustDialogAccepted": true } }`) prevents the trust-dialog variant for all worker terminals spawned under it. Verified end-to-end 2026-09-24 on Orca 1.4.209. Orca 1.4.219+ pre-trusts agent launch folders by default; keep the prompt-failure path for disabled settings and Alpine WSL.

Execution requires CLI ≥ 1.4.205 and a positively ready runtime with a stable appVersion ≥ 1.4.205; a new executable alone never enables an old, unknown, unreachable, or starting runtime. Cache verdicts only for the same resolved runtime. Execution mutations (`POST /api/runs`, `/api/run`, gate resolve) answer `503 execution_disabled` when readiness fails. The UI disables execution and New Run while retaining read-only navigation.

Terminal release (`POST /api/workers/:id/release`) and retention (`POST /api/workers/:id/retain`) require body `runId`. Fresh exact scope checks prevent cross-Run Activity attribution. Protects main, current, active, and unknown resources without terminal-title matching or force-close of unproven panes.

## Web app gotchas

- **`web/src/harness.ts` is the single config store** (`useSyncExternalStore`). The server-side `.orca-dag/config.json` is the source of truth; localStorage is only a one-time migration source plus a write-through mirror. Writes debounce 250ms before `PUT /api/config`.
- **Hydration order matters**: `App.tsx` gates `RunPicker`'s auto-pick behind a `hydrated` flag — if the picker fell back to "newest Run" before `initConfig()` resolved, it would overwrite the stored Run choice.
- The UI polls `GET /api/dag` every 2s. Manually dragged nodes keep their positions across refreshes (only untouched nodes follow auto-layout; ↻ Re-layout bumps `reorgNonce` to clear drags). Layout algorithms live in `web/src/layout.ts` (dagre layered LR/TB).
- **Sectional workbench architecture**: The UI operates as a modern, resource-efficient sectional workbench (`workbench.css`, `styles.css`, `chat-dock.css`, `graph-motion.css`), replacing legacy paper/crayon aesthetics and SVG turbulence filters.
  - **Navigation & Routes**: Navigation provides Chat plus six operational sections (`overview`, `decisions`, `executions`, `activity`, `resources`, `settings`), with seven desktop Dock columns and four narrow columns (Chat, Decisions, Executions, All apps). URL hash routing synchronizes state (`#section=home`, `#section=chat`, `#section=<name>`). Canonical node route is `#section=chat&task=<id>`; legacy `#section=tasks` routes normalize to Chat.
  - **Task Private Chat & Detail Tab**: Clicking a node in the DAG graph navigates to `#section=chat&task=<id>`, opening that Task's private chat at Messages. Complete Task details/configuration (`NodePanel`) mount in a sibling **Task** tab alongside Messages and Inbox checks on first visit and remain mounted across sibling-tab switches for that conversation. `NodePanel` has no independent `h1`, Close button, Escape-to-close handler, or auto-focus; operational action buttons jump directly to the relevant Operations sections. App passes a stable `taskSelection` object until explicit navigation, avoiding poll-driven resets. Run group chat has no individual Task tab.
  - **Lazy Graph Rendering**: `DagView` is lazy-loaded on first view (`React.lazy`) and retained in DOM/memory after initial mount. Nodes use fixed dimensions (280×120px, title 16px, summary 14px) and static dependency lines. Only positively evidenced executing tasks show a pulsing status dot, which automatically pauses when hidden, inactive, or under `prefers-reduced-motion: reduce`.
  - **Persistent Chat Dock**: The right communication dock (`.workbench-chat`, 440px default, resizable 280–820px) uses `useScopedChatState` to isolate drafts, busy status, receipts, and uncertainty flags per Run and conversation scope. Switching Runs isolates drafts and never implicitly retargets messages. On screens `<=900px`, chat switches to a focused single pane hiding the main section.
  - **Shared Event Stream**: One shared `ActivityPanel` SSE connection (`/api/activity/stream`) serves event and presence data, automatically pausing when `document.visibilityState === "hidden"`.
  - **Portaled Execution Controls**: `ExecControls` portals its action buttons (`Run with Orca`, `Stop`, launch preview, status notices) into `.workbench-action-host` in the top header, while execution settings and preflight preferences remain anchored in Settings.
  - **Memory Limits**: V8 JavaScript heap metrics measure only JS heap usage, not browser renderer process or GPU compositor memory. Do not infer GPU/renderer savings from JS heap figures alone.

## Orca integration constraints (also in skill/SKILL.md)

- **`orca orchestration reset --tasks` has NO `--run` scope** — it wipes the *entire* local orchestration DB, every Run at once. To redo one DAG, create a new Run via planning agent or CLI (`orca orchestration run-create`); do **not** reset. The viewer deliberately ships no reset route, no wipe-tasks control, and no in-page New Run button (planning/CLI creates Runs, and the viewer reads existing Runs; `POST /api/runs` remains public), so don't reintroduce them.
- **`task-update` only changes `--status`/`--result`** — no edit to spec/title/deps, no delete-single-task. "Changing a task" = rebuild the DAG.
- **Gates are Run-scoped, but the flag differs by direction**: `gate-list` (read) takes `--run <id>`; `gate-resolve` (mutation) takes NO `--run` — it resolves Run scope from the bound `--from <handle>` (plus a globally-unique `--id`). The viewer binds the coordinator terminal to the Run first via `run-use`, then resolves by `--from`. Every pending gate prevents Run completion, including ordinary approvals with no blocked Task. All gates blocking a Task must approve before release or dispatch; one approved gate cannot override another pending gate.
  Ordinary approval gates accept exact `approve` and `approved`; integration gates still require exact `integrated`. A raw `ready` status is not enough: Orca can set it after resolving only one of several gates, or before dependencies complete. Require completed same-Run dependencies for dispatch, reuse, and explicit retry; dispatch and reuse also require every applicable gate approval. Keep blocked Tasks out of the ready wave and show their dependency/gate reasons in the scheduler. Pending gates keep an otherwise idle Run in `awaiting_input`.
- **`HARNESS_LAUNCH` in `orca.ts` only has `claude --dangerously-skip-permissions` verified.** Other legacy launchers need their own autonomous flag added and verified. Known native-agent refusals (`invalid_argument`, `agent_unconfigured`, or unsupported preferences) park the original attempt, never start a second legacy worker. Opted-in custom commands choose their legacy route before launch. Preserve the separately selected OpenCode/Codex compatibility adapters.
- **Late success corrects an outcome, not custody.** Only authoritative success for the exact Run/Task/Dispatch may correct a provisional `start_failed` attempt. Preserve the start receipt and completed release/retain decisions; stale or rejected reports and another Dispatch cannot clear the failure or trigger duplicate cleanup.
- **Mailbox semantics are version-dependent.** Legacy `check` replays the oldest unacknowledged Delivery and hides later messages; this starved a worker inbox on 1.4.205 (2026-09-22). Process every legacy batch, including rejected/duplicate-only reports, and handle any next batch returned by ACK; questions and custody may defer it. V3 consuming `check` acknowledges on read, while ACK alone does not fetch next. Preserve the exact request identity and durable pending work in `sessions.json` across read failure/restart; transport acknowledgement is not processing completion. Failed worker launches are never auto-retried. `--peek` is observation, not consumption. Hand-rolled loops must follow the runtime-matched guide. Detail lives in `skill/SKILL.md` Boundaries.
