# Compatibility and Verification Matrix

English | [简体中文](compatibility_zh.md)

Back to [README](../../README.md) · [Documentation Index](../README.md)

This document records the supported version floors, runtime verification gates, and historical real-provider test results for the `orca-dag` viewer and coordinator.

> **Important:** Compatibility floors are **not** an exhaustive tested-version matrix. The native-agent and experimental-TUI gates use the **running Orca app version** (`result.runtime.appVersion` in `orca status --json`), not just the installed CLI version. Do not infer verified execution on unlisted versions or agent combinations.

---

## Supported Version Floors

| Capability / launch path | Minimum Orca version | Conditions and boundaries |
|---|---|---|
| **View Runs, Tasks, and gates** | **1.4.160** | Baseline for Run/Task/Dispatch schema (PR #9925). Runtimes 1.4.160–1.4.204 remain view-only (DAG renders, execution controls disable themselves). Older runtimes are unsupported. |
| **Execute DAGs with supervised workers** | **1.4.205** | Execution floor where supervised Dispatch landed. Individual agent launch paths may require newer versions. |
| **Native Codex startup** | **1.4.217** | Local POSIX current/existing workspaces. Older/unknown runtimes and newly created local workspaces retain the compatibility adapter. |
| **Native OpenCode 2 TUI** | **1.4.220** | Requires no per-node model override; the viewer's `opencode` choice maps to Orca's `opencode2` agent. |
| **Explicit Mini / Full TUI selection** | **1.4.222** | OpenCode ≥ **2.1.2**; local Linux current/existing non-lane workspaces. Auto remains the default. |
| **API-preselected OpenCode 2 full TUI** | **1.4.222** | Explicit model + `ORCA_DAG_OPENCODE_TUI=1`; local POSIX current/existing non-lane workspaces only. Default-off and experimental. |
| **Native OpenCode model in Auto** | **1.4.241** | Advertised launch preferences (`orchestration.worker-launch-preferences.v1`); local POSIX current/existing non-lane workspace; no variant or effort. Uses distinct `opencode` agent and execution-host model/CLI verification. |
| **Native OMP / Antigravity (Current / Existing)** | **1.4.245, both running runtime and resolved CLI** | Local Linux Current or exact Existing placement only, no lanes. Native `worker-start --agent omp` / `--agent antigravity`, opaque `--model` or configured default, no nonempty effort. Orca chooses Chat/Terminal from user settings; the viewer neither checks nor overrides that preference. Terminal TUI and OMP Native Chat evidence are distinguished below; see [fleet visibility limits](../tutorials/viewer-operations.md#known-limitations). |
| **Native OMP / Antigravity (New worktrees & lanes)** | **1.4.246, both running runtime and resolved CLI** | Local Linux only. Supports `new-child` (requires verified local managed Git parent) and `new-top-level` (requires exact repository `id:` or absolute `path:` Git repo; rejects ambiguous names, plain folders, foreign hosts, and auto git-init). Workspace lanes share workspace ONLY: first Task creates or adopts it, dependency-ordered followups use exact Existing; every Task gets a fresh native agent session and Dispatch (no generic terminal reuse, `--terminal`, or `--surface` override). Admission and preview validate the lane's seed placement and fail before mutation on older versions. All nonempty effort remains rejected. |

## Path Boundaries and Historical Findings

- **Native OpenCode 2 path:** Passed read-only and isolated-worktree file-writing checks with **OpenCode 2.0.22** (Orca ≥ 1.4.220). This is separate from the experimental API-preselected adapter, whose real-runtime checks ran on macOS with **Node.js 22.23.0** and did **not** cover long coding runs, Git Stage, newly created workspaces, lanes, remote, or Windows execution.
- **Orca 1.4.243 and OpenCode 2.2.0 boundaries:**
  - **Advisory model discovery and manual entry:** Local viewer workspace discovery (`GET /api/models/:harness`, `scope: "local-workspace"`) is advisory and distinct from execution-host model verification. Discovery failure or an empty catalog does not prevent manual entry of valid `provider/model[#variant]`, and saved unlisted models are preserved. Local discovery failure does not change native routing gates or authorize fallback.
  - **Heartbeat authoritative rules:** Heartbeats (`type: "heartbeat"`) provide **liveness evidence only**, never completion or settlement. Orca rejects heartbeat and `worker_done` in group messages (`@all`, `@worktree`); isolated profile preamble preview supports 5m/off/15m intervals without emitting heartbeat commands when turned off, does not alter global user settings, and does not claim unexercised live heartbeat worker execution or hot-reloading worker settings.
  - **Removed-work ledger:** `run-show` optional summary and on-demand cursor pagination (`/api/runs/:runId/removed-work`); missing summary on older hosts remains unavailable rather than zero; historical `activeWorkersAtRemoval` is not a live process check; no reset button is provided.
  - **Explicit Mini / Full TUI and backend visibility loss:** Explicit Mini and Full TUI on OpenCode 2.2.0 both failed the startup identity ready gate during live testing: while the original API session model and location were established correctly, the created terminal did not update its title to `OC | odag:<request>` within the 60-second deadline. The adapter safely refused before Task input or Dispatch, closing the uninputted pane and recording `settledVia=start_failed` with no cleanup debt; neither frontend provides provider task execution coverage on 1.4.243 + 2.2.0. This does not claim that all OpenCode 2.2.0 environments are unconditionally unsupported (root cause is unverified), but the startup identity gate is not relaxed. With no Orca managed OpenCode accounts, multiaccount execution is not claimed as verified. Regression fixtures cover backend visibility loss after pane creation, holding preparation and forbidding `worker-start`, pane closure, or replacement Dispatch for both Mini and Full TUI.
  - **No worker support expansion:** Neither upstream PR 32006 (nativeChat models) nor new-top-level worktree fixes expand worker model support for `opencode2`, new worktrees, variant/effort, or remote/Windows placements. Older compatibility matrices and version floors remain unchanged.
  - **Read-only CLI-run observation:** Existing exact-bound `openai/gpt-6.1-sol#xhigh` sessions were read as provider `active` and `exited`, with assistant-message model evidence and `opencode-api` output, while native fleet remained `unverifiable`. This is observation coverage, not new Task-success, Mini/TUI or worker-harness certification. Provider evidence does not expand retry/Stop/release authority; bounded or unavailable history stays explicit.
- **OMP / Antigravity native policy:** The presets use native `worker-start --agent`, letting Orca select Chat or Terminal from existing user settings. Terminal TUI and OMP Native Chat have separately recorded evidence; Native Chat is neither forced nor rejected based on surface preference.
  - **Placement and version gates:** Local Linux Current or exact Existing requires both running runtime and resolved CLI ≥ 1.4.245. New Git worktrees (`new-child`, `new-top-level`) or any workspace lane require both ≥ 1.4.246. Remote environments, macOS, and Windows are rejected. New-child requires a positively identified local managed Git parent; new-top-level requires an exact repository identifier (`id:...` or absolute `path:/...`) for a local Git repo. Ambiguous names, plain folders, foreign-host repositories, and automatic git-init are rejected.
  - **Workspace Lanes and Fresh Sessions:** A lane shares the workspace ONLY. The first Task creates or adopts the workspace seed; subsequent dependency-ordered Tasks reuse the exact Existing selector. Every Task in the lane receives a fresh native agent session and Dispatch. Generic terminal reuse, `--terminal` or `--surface` flags, and fallback after native refusal are never permitted.
  - **Admission and Preview Gate:** Admission checks and plan preview inspect the lane's seed placement against the running Orca runtime and resolved CLI, failing before any Orca mutation if either is < 1.4.246.
  - **Model, Effort, and Custody:** Opaque model selectors are passed as one native `--model` argument without provider/suffix remapping; an empty override omits the flag. Every nonempty effort is rejected, even with a model. Requested/effective launch, liveness, custody, and unknown receipts retain their native meanings. No provider-session backend is added.
  - **CLI 1.4.246 Orchestration `--full` Compatibility:** When the resolved CLI is ≥ 1.4.246, `runOrca` appends `--full` to orchestration commands (`orchestration *`) because 1.4.246 defaults to concise output even with `--json`, omitting Run ownership, Task specs, and launch receipts. CLI 1.4.245 rejects `--full` on orchestration verbs; the viewer gates this using the existing readiness probe cache before invocation. Mutations are never retried on uncertain or concise responses. Real acceptance verified that a single `POST /api/runs` successfully created `run_2a67b90e6a94` without duplicate mutations or 500-on-concise failures (recorded in `.orca-dag/20261103T024111Z/run-create-api.json`).
  - **Native Chat fleet visibility:** OMP Native Chat execution, viewer recovery and active Stop passed on 1.4.245, but fleet status remained `missing_status`. In fleet investigation, 1.4.246 source/function replay still reproduces the gap; [PR #34068](https://github.com/stablyai/orca/pull/34068) remained unmerged on 2026-11-03. Note that the 1.4.246 placement/lane verification is real runtime E2E execution, but fleet visibility itself still exhibits this upstream gap. Exact live session evidence is not accepted Task completion or permission to replace a worker; raw unknown is preserved and never inferred as dead or replaced. Antigravity Native Chat remains unverified; see the [detailed limitation](../tutorials/viewer-operations.md#known-limitations).
  - **Output and archives:** OMP supports bounded structured transcript reads and normal-release transcript archives; long first-preamble text may be clipped. Antigravity uses honest terminal fallback (`provider_unsupported`) and normal-release terminal archives, not structured provider tool messages or proven provider-session identity. Native owned active Stop succeeded for both, but neither had a usable post-active-Stop archive. Preserve pre-Stop output when needed; do not promise full history or post-Stop archival support.
  - **Historical rejected forced-Terminal design:** Main Run `run_8713a6b6ebfe` correctly recorded both CLI-only certification Tasks as failed. Prelaunch via `agent launch --surface terminal` followed by `worker-start --terminal` produced `external_terminal` custody: settled release retained panes without archives and active Stop returned `stop_unknown / processAction: none`. Antigravity's bound Stop target later sent its own accepted failed outcome, not successful cancellation. These failures reject that design, not the successful independent native `--agent` baselines above. The viewer does not implement the prelaunch-bind route or use native launch as a retry after refusal. Retained resources and uncertain identities from those historical probes stay accounted for; absence never authorizes cleanup.
  - **Evidence boundaries:** The original `REPORT.md` and `matrix.json` pairs under `.orca-dag/20261102-070251-333/certification/{omp,antigravity}/` retain the failed design verdicts and separately named successful native rows. Their CLI-only eligibility fields describe the rejected design, not today's preference-following policy. Separate viewer evidence under `.orca-dag/20261102T084604Z/` covers TUI integration, same-Dispatch viewer crash recovery, owned active Stop and normal-release archive reading. OMP Native Chat evidence is separately recorded under `.orca-dag/20261102T095434Z/` and `.orca-dag/20261102T100646Z/`; the operations tutorial records the Runs and the fleet limitation. Real runtime E2E placement and lane verification is recorded in `.orca-dag/20261103T024111Z/` (with `verification.json` and `plan.json`, local ignored artifacts; not committed documentation), covering OMP user-default Chat and Antigravity user-default Terminal across 4 lanes (OMP child sum 20, OMP top-level sum 21, Antigravity child sum 59, Antigravity top-level sum 97), serial workspace handoff, 8 fresh native sessions, and zero cleanup debt. Does not claim new-placement active Stop/restart, Antigravity Chat, Orca-runtime restart, setup `run`/`inherit`, or explicit-model new-placement live certification.
- **Task readiness prerequisites:** Ordinary approval gates accept only the exact resolved decisions `approve` or `approved`; `integrated` remains an exact separate integration decision. Every gate and every dependency in the same Run must be satisfied before a Task is runnable, even when Orca's task row says `ready`.
- **Verified Built-in Worker Harnesses:** `claude`, `codex`, `opencode`, `omp`, and `antigravity` are selectable within their recorded version and placement constraints; native baseline evidence is distinguished from viewer checks above. Claude Code has a historical end-to-end check on Orca **1.4.209**, but its exact CLI version was not recorded.
- **Unverified Harnesses Refused for Launch:** The five harnesses `gemini`, `grok`, `cursor`, `droid`, and `kimi` have NOT been concretely verified as supervised worker harnesses and are not exposed as built-in presets or launchable harnesses in the viewer. Any node or saved configuration attempting to launch with these unverified harnesses is rejected upfront with an explicit `unverified_harness` error; they are neither silently substituted nor auto-migrated. Historical records and logs created under those names remain readable in the viewer.
- **Experimental Custom Commands vs Bare IDs:** User-defined custom commands require launching with `ORCA_DAG_ALLOW_CUSTOM_COMMANDS=1`, run via the legacy local path without isolated placement, and are NOT a verified support claim. The five unverified bare IDs (`gemini`, `grok`, `cursor`, `droid`, `kimi`) are rejected with `unverified_harness` even when custom commands are enabled.
- **Skill Installation and Planning Independent:** Bundled skill installation and planning support for detected agents (such as Claude Code, Cursor, Gemini CLI, Droid, Grok, Kiro, Qoder, CodeBuddy, Codex, OpenCode, Pi, OMP, Kimi) remain intact and operational, as skill-capable planning and agent skill installation are separate from supervised worker execution verification. Installing the skill for an agent does **not** establish verified worker execution.
- **Older findings:**
  - Codex **0.156.1** on Orca **1.4.209** exhibited missing fleet status (`unverifiable / missing_status`).
  - OpenCode **2.0.15** on Orca **1.4.209** failed native prompt delivery (`input_accepted` receipt without prompt execution).
  - These historical combinations are documented limitations, not recommended deployments.
- For detailed operational limitations, failure modes, and tested workarounds, consult [Runtime findings and launch-path boundaries](../tutorials/viewer-operations.md#known-limitations).
