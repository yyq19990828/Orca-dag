# Orca DAG Viewer 界面评审

**结论：保留现有纸张／蜡笔风格，优先修复操作入口和状态表达。** 目前最大的差距不是“不够好看”，而是部分场景下，用户虽然看到了状态，却无法可靠地进入详情、判断读取是否成功，或在手机上读清具体任务。

范围：`web/src/App.tsx` 及其调用的界面组件。已检查桌面 1440／1280px、窄屏 390／375px、Operations、worker 详情、任务结果、菜单和启动前检查。展示数据全部隔离；另外实际观察了 API 不可用时的界面。**没有执行真实任务，也不是完整 WCAG 审计。**

## 设计专属性

**成立，不建议换成通用控制台。**

虎鲸、纸张网格、蜡笔节点形成了完整的视觉身份。更重要的是，依赖与层级的区分、人工决策入口、Task／Dispatch／请求证据的逐层展开，确实服务于“个人开发者监督并行智能体”。

下一步应让这套身份具备更精确的阅读与交互规则，而不是增加装饰。

## 做得好的地方

1. **Operations 的信息架构贴合实际风险。** “决策与恢复／执行与工作区／历史与诊断”有明确分工。点击待办能切换分类、展开对应记录并定位，不要求用户手工查找 ID。
2. **可读摘要没有吞掉原始证据。** worker 摘要显示任务名，细节保留完整 Dispatch ID；结果中的 `0`、`false`、未知字段和原始 JSON 都能保留。长标识符也能在窄屏记录面板内换行。
3. **安全对话框已有可复用的交互基线。** 启动前检查可以用 Escape 关闭，并将焦点返回触发按钮；文案明确区分预览与实际执行证明。

## 优先问题

### 1. [P1] 节点能获得键盘焦点，却不能打开任务详情

**证据**：独立评估及复核结果一致：节点聚焦后按 Enter、Space，任务面板数量均为 0；点击同一节点后为 1。业务选择入口目前依赖 `onNodeClick`。

位置：`web/src/components/DagView.tsx:1036–1052`、`web/src/App.tsx:468–471`。

**影响**：键盘用户可以到达任务，却无法沿这个主要入口查看结果或执行记录。这直接违背已确认的键盘可操作目标。

**修复方向**：
- 为节点提供明确的 Enter／Space 详情激活行为，或可访问的详情按钮。
- 区分“选择／移动图对象”和“打开业务详情”。
- 增加可见焦点；详情关闭后回到原节点。不要给普通非模态侧栏强加焦点陷阱。

**对应命令**：`$impeccable harden web/src/components/DagView.tsx`，随后针对键盘路径运行 `audit`。

### 2. [P1] 首次读取失败，被同时呈现为“空项目”和“旧状态”

**证据**：没有 API 后端时，页面同时显示：
- “暂无 Run”“暂无阶段”；
- “正在加载任务…”；
- “当前显示上次读取的状态”；
- 中央的新手空白页，引导用户先生成任务。

该标签页没有成功读取过 DAG。点击“启动前检查”又增加了英文 session-token 错误。

位置：`web/src/App.tsx:804–811`、`web/src/components/DagView.tsx:1010–1021`、`web/src/components/RunPicker.tsx:234–237`。

**影响**：用户无法区分“确实没有任务”和“任务没有读出来”，可能去重新规划，而不是修复连接。

**修复方向**：
- 明确区分首次加载、成功但为空、首次读取失败、保留上次成功数据四种状态。
- 仅在确有历史数据时显示“上次读取”提示。
- 失败时给出一个主要恢复入口和可读说明；原始诊断保留在技术详情中，不删除证据。

**对应命令**：`$impeccable harden web/src/App.tsx`，配合 `clarify` 整理错误与恢复文案。

### 3. [P1] 手机上的任务图变成缩略图，不能完成“快速查看”

**证据**：390px 宽度下，全图缩放约为 `0.288`；任务节点约 `61×21px`，原本 14px 的标题视觉尺寸约为 4px。顶部区域和调度器仍清晰、占据显著空间，真正需要监督的任务反而难以阅读。桌面部分状态、提示文字也只有约 10–11px。

位置：`web/src/components/DagView.tsx:950–975`、`web/src/stage-card.css:4–60`。

**影响**：即使手机不承担完整执行操作，也应能读清“哪个任务失败、谁在运行、哪里需要我”。目前仍需缩放、平移和试点微小节点。

**修复方向**：
- 窄屏优先提供可读的任务／待办清单，DAG 保留为可切换的依赖全景；或者提供阅读级的任务／路径聚焦。
- 调度器压成可展开摘要，让任务内容获得主要空间。
- 状态、风险和证据文字采用更可靠的字号与对比度；保留纸张和节点轮廓的个性。

**对应命令**：`$impeccable adapt web/src/App.tsx`；文字与对比度另做针对性 `audit`。

### 4. [P2] 窄屏菜单没有约束在视口内

**证据**：
- 390px 下，“视图”菜单左边界约为 `−37px`，部分图例和“重新布局”被裁切。
- 375px 下，展开执行设置后面板右边界约为 `664px`，产生横向溢出。

位置：`web/src/compact-header.css:492–501,551–553`。

**影响**：这不只是手机不支持完整配置的问题；已有入口会把内容放到用户看不到的位置，连查看图例也受影响。

**修复方向**：窄屏使用统一的视口内面板，或进行左右碰撞修正；设置固定边距、最大高度和内部滚动。仅限制宽度不足以解决锚点偏移。

**对应命令**：`$impeccable adapt web/src/compact-header.css`。

### 5. [P2] 启动前检查要求用户记住 Task ID，并扫描大量重复文字

**证据**：六任务预检仅显示 `task_0…task_5`，没有任务名；相同模型、工作区、路径、原因和限制逐任务重复。375px 下，消息区域可见高度为 360px，内容高度约为 1366px。

位置：`web/src/components/ExecControls.tsx:255–292`、`web/src/components/DecisionDialog.tsx:187–190`。

**影响**：最需要仔细核对的时刻，反而依赖跨屏记忆和长文本扫描；差异与特殊风险容易被重复内容淹没。

**修复方向**：
- 显示任务名，完整 ID 可展开或复制。
- 先列共同默认配置，再突出逐任务差异、未知与特殊限制。
- 保留“不自动换路径”“预览不等于执行证明”等边界，不把精简做成风险隐藏。

**对应命令**：`$impeccable clarify web/src/components/ExecControls.tsx`，配合 `distill` 重组预检信息。

## 认知负荷与情绪路径

认知负荷清单 **5/8 项未通过**：单一焦点、信息分块、重要性层级、选择数量、跨屏记忆。问题集中在窄屏和高风险细节，不意味着整个首屏都混乱。

超过四项的具体位置是默认 harness 的五个同层选项，以及 worker 详情并列呈现的六类动作。后者在展示场景中多数禁用，**不能把它们说成六个可执行选择**。六类任务状态也不是决策菜单，不计作选择过载。五个合法 harness 不需要删减，重点是解释支持边界。

**情绪路径推论**：进入时亲近、全局感明确 → 待办定位带来掌控感 → worker 多套状态增加理解成本 → 预检的纯 ID 和重复文字削弱安心感。API 不可用时，互相冲突的提示会进一步破坏信任。这里没有真实用户访谈或完成运行后的体验证据。

## 不同用户会在哪里受阻

- **Alex，高频个人开发者**：能从待办快速定位记录，但预检突然只剩 ID，需要回忆任务映射；worker 动作区缺少明确的阅读顺序。
- **Sam，键盘／低视力用户**：焦点能到节点，却打不开详情；节点焦点提示不明显，菜单和详情的退出行为也不统一。
- **Casey，手机上间歇查看进展的开发者**：只能先辨认节点颜色，再缩放寻找任务名；菜单裁切进一步增加查看成本。直接进入 worker 后，记录换行表现较好，应保留。

## 次要观察

- 已完成任务的结果后仍展示较多锁定配置，可默认折叠为“启动配置（已锁定）”，但保留完整历史。
- worker 动作宜按“检查证据／终端处置／执行介入”分层，不要把停止、放弃、释放混为一种清理动作。
- 将安全对话框已有的关闭与焦点返回规则，延伸到其他浮层；不要简单把所有面板改成模态框。

后续最值得确定的产品取舍：**手机默认服务于“看依赖全景”，还是“几秒内确认是否需要介入”；预检服务于“列出所有配置”，还是“帮助发现差异与风险”。**
